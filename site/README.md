# co:op website

This folder holds co:op's two landing pages, sandbox and overnight walkthroughs, docs overview and
generated reference pages, and GitHub Pages serves them from here. The pages are static HTML, CSS
and JavaScript, with no framework, no build step at serve time and no `node_modules`. The look
follows `brand/DESIGN.md`.

```
site/
  index.html            the homepage, the sandbox story (generated: never edit it by hand)
  orchestrator.html     the second landing, one night of coop loop (generated: never edit it by hand)
  docs.html             the docs (hand-written, except its generated terminal windows)
  sandbox-guide.html   first sandbox walkthrough (generated from tools/site/sandbox-guide.tpl.html)
  claude-code-sandbox.html, codex-sandbox.html, gemini-cli-sandbox.html, grok-cli-sandbox.html
                       provider-specific setup, access checks and first reviewed run
  overnight-guide.html first unattended queue (generated from tools/site/overnight-guide.tpl.html)
  networking.html etc.  references generated from docs/*.md and MIGRATING.md through one shared template
  search-index.json     every docs section, for the docs' search (generated by make docs)
  llms.txt              the CLI reference for language models (generated by make docs)
  site.webmanifest      PWA manifest (name, theme color, app icons)
  robots.txt            allow-all + sitemap pointer
  sitemap.xml           generated inventory of every canonical public page
  CNAME                 the custom domain, coop.dryga.com
  README.md             this file
  assets/
    css/site.css         the design system, shared by every page
    css/orchestrator.css the Orchestrator page's story: the night board and its task element
    js/site.js           copy buttons, the agent picker, the homepage story, the scenes, the docs menu, contents and search
    js/orchestrator.js   the Orchestrator page's story: the night replayed on the board, the sandbox building itself
    js/analytics.js      Mixpanel: autocapture, page views, session replay and successful copy intent
    fonts/               Inter (SIL Open Font License)
    img/                 favicon, app icons, the two social cards (see "SEO assets"), the Coop mark and
                         wordmark, zed-coop.png, and the Emisar and Ryker logos
```

## Preview locally

Any static server works:

```bash
cd site && python3 -m http.server 8000
# open http://localhost:8000
```

## The landing pages and the docs' terminals

`make docs` (`go run ./tools/gendocs`) writes `index.html` from `tools/site/index.tpl.html` and
`orchestrator.html` from `tools/site/orchestrator.tpl.html`, with the night board drawn at morning
so the page reads whole without JavaScript. It fills in the parts that repeat, so nobody types them
by hand: the icons, the provider marks (`tools/site/logos/`), the terminal scenes and the commands
you copy, all drawn in `tools/gendocs/scenes.go`.

The homepage's commit count is a plain number in its template. To update it, fetch co:op, Emisar
and Ryker, add up the commits on each `origin/main` that carry a `Coop-Task:` trailer other than
`none`, and edit the number:

```bash
git log origin/main --grep='^Coop-Task: [^n]' --oneline | wc -l   # in each of the three repos
```

The tool also fills the terminal windows in `docs.html`. You write the docs by hand, except between
a `<!-- gen_site: NAME -->` and `<!-- /gen_site -->` marker, where the tool writes the scene named
`NAME`, and the `gen_docs_nav` and `gen_docs_pager` regions, where it writes the docs menu and the
previous and next links.

## The docs' map

`docsPages` in `tools/gendocs/references.go` is the one map of the docs: each page's group, label
and place in reading order. The menu, previous and next, `docs/README.md`, the search index and the
routes of generated pages all come from it. A page with no entry fails the tests.

Every docs page has three columns across the whole page: the menu, the article and that page's
contents. Keep the menu and the contents apart, the side columns quiet, and the article at its
reading width and type.

Keep `docs.html` reading as one guide, and end each section with a `.doc-more` link to the page that
goes deeper.

Readers read the docs on the website, so publish what they need there and link it there. Links to
GitHub are for source code, examples and the files in the menu's Project group. The README links
website pages, not `docs/*.md`.

Search runs in the browser over `search-index.json`, one entry per section, with no outside service.
To keep something out of the index, add it to `leftOutOfSearch` in `tools/gendocs/search.go`. If
readers search for a word a page doesn't use, add it to that page's `Keywords`.

The guide pages, including the provider-specific sandbox guides, are generated from their
`tools/site/*.tpl.html` templates, with the same typography, external-link treatment and asset
versioning. Edit the templates and run `make docs`. Don't edit generated guides.

The guides use the shared `.guide` styles: an introduction with a short lead and an ordinary
prerequisite list, in the article's column, followed by numbered instructions. The contents start
beside the introduction, on the same top line. When you write a guide:

- Keep the line length comfortable, and start both columns directly under the header.
- Use checkpoints the reader can observe, and native disclosures for optional content. Avoid
  repeated overviews.
- For an optional explanation, use `.guide-detail.guide-help` with a small decorative question icon
  beside the summary. The existing plus/minus remains the expand/collapse control.
- Commands that belong together can share one copy control. Join dependent setup steps with `&&` so
  a failed command stops the block. Keep interactive approvals and pasted run-ID inputs separate.
- Use `.code-file` to show what the reader adds to a file.
- Put a command and its sample output in one `.terminal-example`, using the existing `.cmds` rows
  and a sibling `pre.code > samp`. Attach each output to the command that produced it.
- Keep the host or agent context outside the block. Use short platform labels only when results
  differ.
- The copy source must contain the command alone. Give long scripts a short `data-copy-label` for
  their copy button.
- Keep output visible without JavaScript, and avoid per-output captions.
- Keep the worked example in one declared workspace. When the example resumes a run, repeat the
  queue selection.

Platform-specific example output can use `[data-terminal-outputs]` with uniquely identified
`[data-output-platform="macOS"]` and `[data-output-platform="Linux"]` panels. Keep each panel's
`.terminal-platform` label in the HTML, and keep the shared command outside the panels so it has one
copy button. The shared script adds tabs above the command, and selects Linux for a reported Linux
platform and macOS otherwise. Without JavaScript, both labeled outputs remain readable.

Check new public copy for plain English. Use [Humanizer](https://github.com/blader/humanizer) where
wording is staged, repetitive or unnecessarily formal. Keep the technical voice, and check that each
rewrite preserves the facts, commands, examples and safety limits. Edit prose in its source, keep
heading anchors stable, and regenerate before you check the rendered page.

Before you publish a guide:

- Check its instructions against the current source, and try to prove them wrong.
- Inspect its desktop, mobile, keyboard, no-JavaScript and copy-failure behavior.
- Keep the review findings and screenshots in the task that owns the guide.

See the [public walkthrough rule](../.agent/kb/rules/public-walkthroughs-have-reader-proof.md).

The public reference pages (`networking.html`, `box.html`, `agents.html` and the other `docsPages`
entries with a `Source`) come from `docs/*.md` and `MIGRATING.md`, so edit the Markdown once for
GitHub and the website. Goldmark renders CommonMark/GFM into
`tools/site/reference.tpl.html`, and the generator adds headings and contents, scrolling tables,
the menu, metadata and sitemap entries.

A new Markdown topic needs an explicit entry in `docsPages`, and you must remove a retired
generated page. The drift check fails otherwise.

Markdown links to published references become local `.html` links with their fragments, and links
to source code and examples stay on GitHub. One `make docs` run updates both the
Markdown and the website version of the CLI reference. The CLI source's explicit command separators
become sections, and its help bodies stay verbatim.

Unlabelled blocks and shell examples stay selectable. Shell fences may combine alternatives or
destructive commands, so they don't get a whole-block Copy button unless the author marks one as a
single command to copy, with `` ```bash copy `` (or `` ```bash copy-install `` for the install
command, which analytics counts separately). Config fences copy as one file
snippet.

Copy measurement uses `content_copy_succeeded`, with `measurement_version: 2`, after the clipboard
write resolves. `kind` is `install`, `command` or `configuration`. Copied text is never included.
This measures intent, not installation or activation. The `install_command_copied` events in the
analytics counted every copy-button click, including unrelated commands and failed writes. Keep the
two event series separate.

```bash
make docs         # regenerate after editing a template or a scene
make docs-check   # fails if any page is stale, then runs the site's content tests
```

The terminal scenes copy the CLI's real output. `terminalSources` in `tools/gendocs/site.go`
lists the sources for each terminal: the approved transcripts under
`internal/cli/testdata/approved/` and the Go code that prints each line. When that output changes,
`make docs-check` fails until the scene matches again, and names the page, the terminal and the
line.

Every page loads the stylesheets and scripts with `?v=` and a short hash of those files, so browsers
fetch the new copy instead of reusing a cached one. `make docs` writes the hash, so regenerate after
you change any of them. `make docs-check` fails until you do.

## Deploy

`.github/workflows/pages.yml` uploads `site/` to GitHub Pages on every push to `main` that
touches it, `install.sh` or the workflow itself, and you can also start it by hand. It publishes the
committed files, plus the repo's `install.sh` beside them, so `coop.dryga.com/install.sh` is always
the script on `main`.

You set it up once: in the repo, open Settings → Pages and set Source to "GitHub Actions".

## SEO assets

The favicon, the app icons and the two social cards under `assets/img/` are committed images,
redrawn by hand with headless Chrome and ImageMagick when the mark or a landing page's first screen
changes. `zed-coop.png` is a real Zed screenshot, cropped by hand (see `.agent/kb/website.md`).
Work in a scratch folder and copy the results into `assets/img/`. Below, `$CHROME` is the Chrome or
Chromium binary.

The navigation and footer use local copies of `brand/assets/coop-mark.svg` and
`coop-wordmark.svg`. Don't retype the logo. The icons use the matching tile,
`brand/assets/coop-flat.svg`, and `favicon.svg` is a copy of it. Change those copies together. The
README uses the supplied dark/light vector lockups. `.github/assets/coop.png` is a 512px avatar
export of the same tile.

Draw the mark at 1024×1024 (an HTML page holding the SVG at `100vw` by `100vh`) and scale it down:
`icon-192.png`, `icon-512.png`, and `favicon.ico` bundling 16, 32 and 48. `apple-touch-icon.png`
(180) puts the glyph on a square tile with no rounded corners, since iOS rounds them.
`icon-maskable-512.png` also scales the glyph to 64% around the center, inside Android's round mask.

```bash
"$CHROME" --headless=new --hide-scrollbars --user-data-dir="$(mktemp -d)" --default-background-color=00000000 \
  --window-size=1024,1024 --screenshot=tile.png "file://$PWD/mark.html"
magick tile.png -resize 512x512 icon-512.png
```

Each social card is its landing page's first screen at 1200×630: `og-image.png` for the homepage
(the sandbox picture finished) and `og-orchestrator.png` for the Orchestrator page (the board at
morning). Save a copy of the page with `<base href="file:///…/site/">` in its head, every
`<script>` removed (headless Chrome runs scripts even with `--disable-javascript`), and this style
before `</head>`:

```css
/* the homepage */
.nav-links { visibility: hidden; }
.actions, .story-steps, main > section:not(.story), footer { display: none; }
.story { padding-top: 8px; }
.story-lead { min-height: 0; }
.stage { grid-row: 1; height: auto; }

/* the Orchestrator page */
.nav-links { visibility: hidden; }
.actions, .night-steps, main > section:not(.night), footer { display: none; }
.night-lead { min-height: 0; padding-block: 72px 0; }
.night-stage { position: static; height: auto; padding-top: 40px; }
```

```bash
"$CHROME" --headless=new --hide-scrollbars --user-data-dir="$(mktemp -d)" --allow-file-access-from-files \
  --force-device-scale-factor=2 --window-size=1372,720 --screenshot=card.png "file://$PWD/card.html"
magick card.png -resize '1200x630!' -strip og-image.png
```

Redraw a card after you change its page's hero. If the site ever moves off `coop.dryga.com`, edit
the canonical and `og:url` base, and `site/CNAME`.
