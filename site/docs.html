Documentation

How to run coding agents you don't fully trust, safely and at scale. Each part explains what it does and why it works that way.

The idea

Coding agents do their best work with the guardrails off, free to edit any file and run any command without stopping to ask. That's exactly when you don't want one loose on your laptop.

In a terminal or loop run, co:op runs the agent in a disposable container that sees only the repo you're working on. Your home folder, SSH keys, cloud credentials and other projects aren't in it. The repo's own secrets, like .env files, private keys and a secrets/ folder, are emptied before the agent starts.

Why it's built this way

In terminal and loop runs, the container limits what the agent can reach to its mounted repo. An editor session over ACP also passes the agent's requests for files and terminals on your computer to the editor, so read the editor security note before you use one.

The same box runs interactive sessions, forks, unattended loops and preset roles. With ACP, the editor's own permissions are a separate boundary.

Install

One binary: no Go toolchain, no clone. co:op runs on macOS and Linux (amd64 or arm64) with Git and a container runtime.

curl -fsSL https://raw.githubusercontent.com/AndrewDryga/coop/main/install.sh | sh

This puts coop in ~/.local/bin. If a container runtime is installed, it also builds the sandbox image and runs coop doctor. If not, run that step yourself once you have one:

coop build --egress open && coop doctor

Docker is the default and fully supported runtime. You can choose Apple container (macOS 26+), but not every co:op feature is qualified on it yet. co:op detects both and prefers Docker. The coop binary is fully static, with no other dependencies.

The one-line command trusts GitHub and the repository's main branch, since it runs the downloaded script. The script always checks the release checksum with a local SHA-256 tool and stops if it can't. With cosign on your PATH, it also checks that the checksum came from the exact release workflow and tag. To verify the download before running anything, follow the manual steps. To build from source: git clone https://github.com/AndrewDryga/coop && cd coop && make install.

Quickstart

The shortest path from nothing to a sandboxed agent.

cd ~/code/your-repo  # 1. any Git repo
coop login claude    # 2. sign in once
coop init            # 3. set up the project
coop claude          # 4. an agent in the box, secrets hidden

That's the everyday flow. For a bigger or riskier change, hand the work to a fork instead, and review the result like a pull request. Before you start the fork, fill in the generated task.md: the problem, what done means, the approach and the subtasks.

coop tasks add "Add --json"      # 1. queue the work as a task
coop fork feature claude --loop  # 2. a fork works on it
coop fork review feature         # 3. review it like a PR
coop fork merge feature          # 4. merge it into your branch

Arguments after the agent's name go to the agent, so coop claude --continue resumes your last session, still in the box. co:op keeps its own options, like --peer and --egress; put them after -- to pass them to the agent instead. The rest of this guide goes feature by feature.

The sandbox

What's inside the box, what's left out on purpose, and why that line is the whole security model.

In a normal run, your repo is mounted into the container at the same path it has on your machine. The agent edits your real files, so you see changes land live in your editor, and absolute paths match between co:op, the loop and your IDE. Apart from the agent's own sign-in folder and a shared cache for dependencies, nothing else from your disk is in the container.

Your Git identity, not the box's

The container has no ~/.gitconfig of its own, so co:op mounts a trimmed one: your name and email (commits are authored as you), your global gitignore, and commit.gpgsign=false. Your signing key never enters the box, so commits made in it are authored by you but unsigned.

If you sign your commits (commit.gpgsign=true in your global Git config), co:op signs the box's commits on your computer, where your key lives: when an interactive run exits, after each coop loop cycle, and when coop fork merge merges a fork. Commits from an editor session aren't signed for you; coop sign signs the current branch's unpushed commits. Your history ends up signed by you, so a protected main that requires signatures accepts an agent's work. More on forks below.

Secrets stay out

Files that look like secrets are hidden from the agent by name. Secrets inside ordinary files aren't, so coop check-secrets finds them for you to move out.

Files and folders that look like secrets, such as .env, *.pem, *.tfvars, secrets/, .ssh and a long list of well-known names, are shadowed: an empty read-only folder covers each secret folder, and an empty read-only file covers each secret file. The agent sees that the file exists, but it's empty and can't be written. Templates (*.example, *.sample, *.template) stay visible on purpose, so the agent still learns the shape of your config.

The boundary you control is .coopignore, not .gitignore. A normal run mounts your whole working tree, so a secret Git ignores but that is still on disk (a real serviceAccount.json, say) is visible to the agent. Ignoring it in Git does not hide it. Anything that must live in the tree but stay secret belongs in .coopignore.

The built-in list can't know your repo keeps live keys in config/stripe.live.json. Add a .coopignore at the repo root, one pattern per line, and those paths are hidden everywhere in the box. Comments go on their own lines:

# a file name, hidden at any depth
prod.yml
# a path from the repo root
config/stripe.live.json
# a folder, hidden whole
vault/

That covers secrets you can name. But a token can also sit inside an ordinary file, where the box can read it. coop check-secrets scans the files you'd commit for known provider token formats and long random-looking values assigned to secret-named keys, and reports each as file:line. Add --include-ignored to scan the files Git ignores too, which the box can still read. It exits non-zero when it finds something, so it works as a pre-flight or CI check; a false positive you've reviewed goes in .coopsecretsignore.

Networking

A filtered box reaches its AI provider and the destinations you approve. Everything else is blocked, for every tool in the box.

coop init sets a new project to filtered networking (egress: filtered in .agent/project.yaml). The box then reaches its provider's own endpoints, like api.anthropic.com for Claude, and the destinations your project asks for once you approve them. The block works on the network itself, not through a proxy setting, so curl, an SDK and any subprocess hit the same wall.

To let the box reach more, add a rule under box.egress_rules in .agent/project.yaml, then approve it:

box:
  egress: filtered
  egress_rules:
    - to: {domain: "docs.example.com"}
      protocol: tls
      ports: [443]
coop approve              # review and approve requests
coop net                  # what a new run here can reach
coop net inspect          # a run's connections and blocks
coop net blocked <host>   # how to allow a blocked destination

A rule takes effect only after you approve it in your terminal, so an agent can't widen its own access by editing the file. The other settings are open (everything) and offline (no network); open needs your approval too. With an API key, filtered networking also keeps the real key outside the box: the agent gets a stand-in that works only for that run.

The first filtered run on a computer checks once that the host can enforce the rules; coop net setup does it ahead of time. The networking guide lists every kind of rule and what each provider can reach.

Prove it

Security you can't verify is just a promise. coop doctor attacks its own box and shows you, check by check, that it holds.

Run it any time, and especially after you change your config or update co:op. It builds a throwaway project with test secrets, starts the box and tries to break out. It checks that the secrets read as empty and can't be written, that the box has no way into your computer and no root privileges, that offline mode is really offline, that tasks and credentials stay scoped to the run, and that a fork carries neither the secrets nor anywhere to push to. Your own files and credentials are never the test data. If a check fails, it tells you what to fix.

Run an agent

The everyday command: an agent in your repo, in the box, with no permission prompts.

coop claude           # Claude Code, no permission prompts
coop codex            # the same box, with Codex
coop gemini           # or Gemini
coop grok             # or Grok
coop shell            # a shell in the box, to look around
coop run -- npm test  # run one command in the box
Why skipping the prompts is safe here

Each agent starts with its most autonomous flags on purpose. Outside a sandbox that's reckless; inside one it's the point. The agent doesn't stop to ask at every step, and the box keeps it away from anything that matters.

Forks

Hand work to an agent the way you'd hand it to a contractor: it works in its own copy, you review the change like a pull request, and you decide what gets merged.

A fork is a disposable local clone of your repo, handed to the agent instead of your working tree. Its origin is a local path, so the agent has nowhere to push. A clone carries only committed files, so the secrets Git ignores never come along.

When to reach for a fork

Use one for anything bigger or riskier than a quick edit, or to run several attempts at once. The agent never touches your checkout, so you keep working while it does, and only you merge anything.

It works like a pull request: open, work, review, merge. coop fork review shows the fork's commits and changed files; read the diff in your terminal or your IDE. Merging rebases the fork onto your current branch, for a linear history. The rebase runs on your computer, where your key lives, so the commits can be signed even though the box made them unsigned.

Set your project's checks with gate: in .agent/project.yaml (like gate: make check; coop init leaves the line there, commented out). The merge runs them in the box on the rebased code, before your branch moves. If they fail, nothing is merged and your branch is untouched; coop fork review --gate runs them early.

The merge also stops on anything risky coming in: secret-shaped content, files over 5 MB, and files that run on your computer, like Git hooks, .envrc, editor and agent settings, Compose files, Dockerfiles, CI config and new npm install scripts. Review them, then merge with --force; the checks still run.

A fork's loop works tasks from your project's .agent/tasks/ queue, one at a time. They stay in progress while you review the fork, and merging it completes them. coop tasks watch follows progress across your project and its forks.

Second opinions

For the hard calls, the lead can ask a model with different blind spots, while one agent stays in charge of the code.

Add --peer <agent> to an interactive run, a loop, a fork's loop or an ACP entry. A peer is a target: you can pin its model and effort, but not its account. Only those peers' credentials are mounted. coop-consult runs them read-only; the lead still decides, edits, runs the checks and commits. A preset's consult roles use the same wrapper, with role names, model ladders and personas.

Why it stays simple

There's no extra service or protocol. Asking a peer is optional, kept for hard or risky calls, and only the lead can do it, so a peer never asks another peer or writes to the repo.

coop claude --peer codex --peer gemini  # second opinions
coop acp claude --peer codex            # the same, in an editor

Credentials and failover

Sign in to more than one account, so a long run never stalls on a usage limit.

Sign in to several subscriptions as named credentials. When a loop hits a limit on one, it moves to another and keeps going. It waits only when every account is at its limit.

coop login claude@work      # sign in to a work account
coop login claude@personal  # and a personal one
coop credentials            # list accounts and sign-ins

To use an API key instead, put ANTHROPIC_API_KEY (Claude), OPENAI_API_KEY (Codex) or GEMINI_API_KEY (Gemini) in ~/.config/coop/agents/env. Keys need filtered networking (--egress filtered): co:op keeps the real key outside the box and gives the agent a stand-in. Other Claude and Codex token variables, Vertex's GOOGLE_API_KEY and Grok's XAI_API_KEY are refused. The credential reference lists every supported way to sign in.

co:op treats a key in that file as the provider's default credential. A bare KEY line copies the value from your shell, and is skipped when it's unset; a later line wins over an earlier one. The key stands for one default account, not extra ones: when a named account you signed in to runs, co:op leaves the key out so it can't override that account, even if it's the default.

There's no pool to set up: a loop rotates through whatever its lead's target ladder expands to. A bare provider:model step fans out across every signed-in account (the default first), so a loop uses all your accounts with no setup; a pinned provider:model@account runs on just one. Limits are tracked per model and account, so claude:opus@personal stays usable while claude:opus@work waits for its reset. Choose the account a plain coop <agent> uses with coop credentials <agent> <name> default.

Each provider uses only its selected account, and API keys stay outside the box. When a loop switches accounts, its progress carries over in the queue and the repo, since each iteration starts a fresh run anyway.

Check limits and usage

coop usage shows each credential's current limits and reset times, and what its last 30 days of tokens would cost at API prices. coop usage codex@work shows one credential without changing your default. The estimate includes subscription use but isn't a bill. It marks partial history, missing prices and editor history it can't tie to a credential; use on the web, on phones, on other machines and charges that aren't tokens are left out. Reading a Gemini sign-in's quota needs Docker and the current co:op base image; it reads the saved sign-in and sends no prompt.

Pick the model

The model is its own choice: pick it per run in the target (claude:opus), or keep it in a preset. A credential is just an account; models don't belong to it.

coop claude:opus        # one run on the big model
coop claude:opus/xhigh  # at extra-high reasoning effort
coop claude:opus@work   # on a specific account
coop frontier           # a lead and its roles, from a preset
coop models             # the models each agent offers

The most specific choice wins: the model in the target (claude:opus), then the current ladder step's model (a loop stepping through a preset), then COOP_<AGENT>_MODEL, then a model inside COOP_<AGENT>_CMD, then the agent CLI's own default. co:op never validates a model name: whatever the agent's CLI accepts works, and a wrong one fails with the agent's own error. New models work the day they ship.

Reasoning effort works the same way: add /effort to the target (claude:opus/xhigh, codex/high), one of low, medium, high, xhigh or max. co:op passes it straight to the agent's CLI (Claude's --effort, Codex's model_reasoning_effort, Grok's --reasoning-effort) without validating it. Gemini has no effort flag, so co:op sets its thinking instead and checks the level first: low or high, on the models it can map (a thinking setting you pin for a model in your own Gemini settings still wins). Effort follows the same order as the model. Targets, the ladders in presets and .agent/loop.yaml, and COOP_<AGENT>_MODEL all accept model/effort (like opus/high); there's no separate effort variable.

That makes the orchestrator pattern cheap. coop init installs the workflow skills but commits no starter subagents; put named roles in a preset and co:op generates each role's wrapper inside the box. A lead on a bigger model spends its tokens on planning and on putting the results together, while each delegated turn bills at the role's model. Add --peer codex --peer gemini and the lead can also ask those agents for read-only second opinions, with no plugins.

Presets

A lead model, its fallback ladder and the roles it hands work to, written once in a file instead of rebuilt from flags every time.

You can wire up the orchestrator pattern by hand: a model here, a --peer codex there. A preset keeps the whole recipe in .agent/presets/<name>/preset.yaml: who leads, on which models, and the named roles it can hand work to. Run it by name wherever you'd name an agent: coop <name>, coop loop <name>, coop acp <name> or a fork.

coop presets init   # write the starter "frontier" preset
coop presets        # list presets (a broken one shows its error)
coop loop frontier  # run the loop with it

The lead's agent: holds one target or a fallback ladder of them, the same ladder a loop rotates through (a bare provider:model fans out across every account; provider:model@account pins one). Each role sets a mode that decides how the lead reaches it:

Mode What it is
native A subagent inside the lead's own session, with no separate box. co:op generates it in the box (coop-<role>, from the role's model and prompt) in that agent's own subagent format, or set subagent: to reuse one you have. Because it runs in the lead's session, every lead in the preset must use the role's provider; if one doesn't, co:op stops before starting and names the role to change.
consult A read-only peer, asked with coop-consult <role>. It runs the role's target or ladder, with the role's prompt as its persona, and can't edit files.
delegate A worker that can write, run with coop-delegate. It may edit the working tree but never commits; the lead reviews the diff, runs the checks and commits. It falls back to the next model only while the tree is unchanged. 
# An example preset.yaml, with a role in each mode
lead:
  agent: [claude:claude-fable-5, claude:claude-opus-4-8@work]
roles:
  thinker:                        # thinks in the lead's session
    mode: native
    agent: claude:claude-opus-4-8 # a coop-thinker subagent
    prompt: roles/thinker.md
  critic:                         # read-only cross-vendor review
    mode: consult
    agent: [codex:gpt-5.6-sol, grok:grok-4.5]
  fast:                           # cheap work that edits files
    mode: delegate
    agent: [gemini:gemini-3.5-flash, codex:gpt-5.4-mini]
What co:op generates from it

co:op turns the YAML into instructions for the lead (each role, when to use it, and the exact command) and mounts the coop-consult and coop-delegate wrappers. A native role's subagent (coop-<role>) is generated in the box from the role's model and prompt, never written to your repo. coop presets init writes starter prompt files under roles/; a target you give on the command line (claude:opus@work) still overrides the recipe.

Consult and delegate ladders skip providers you haven't signed in to; every usable step's credentials are mounted in the lead's box. A consult that falls back replays its saved conversation; a delegate falls back only if every file and the Git history are unchanged.

Evaluations

Compare models, presets, loop recipes or co:op builds on repeatable tasks. A separate verifier grades the finished work; the model doesn't grade itself.

Start with a free preview

The shipped core suite has three small coding tasks. This command launches no container or provider and spends nothing:

coop eval run core codex --timeout 35m --dry-run

For a real run, sign in with coop login codex, and have a working container runtime and a current co:op box image. If the image is missing, run coop build --egress open from a folder without a project Dockerfile. Building may download dependencies.

coop eval run core codex --timeout 35m
coop eval inspect

A real run uses your provider account and may spend credits. A preview checks the plan, not your credentials or whether the runtime is ready. --timeout is a total time limit, not a money cap; each case also has its own timeout. More configurations or repetitions mean more paid work.

Compare before and after

  1. Run a suite and inspect the result.
  2. Change your model, preset, loop recipe or co:op build, then run the same suite with the same number of repetitions.
  3. Use coop eval runs to find the two run IDs, then coop eval compare <before-id> <after-id>. The argument order decides which run is the baseline. Inspect and compare show each configuration's short fingerprint and co:op build.

Choose a suite

  • core: three single-agent tasks. Use provider targets, such as codex:gpt-5.6/xhigh, not presets.
  • queue: ten tasks through the real loop, including review and signoff. Use targets or presets, and allow hours, not minutes. For your frontier preset, try coop eval run queue frontier --timeout 2h. Add --loop-config .agent/loop.yaml to test your recipe.
  • Your own: coop eval init ./evals/my-suite creates a working example. Edit suite.yaml, files/greeting/ and the separate verifiers/greeting/verify.sh. The verifier's README explains grading.
  • An example in the source tree: examples/evals/maintenance/ has three independent shell, Python and Node maintenance loops and unpaid grader controls. It isn't an official benchmark or a shipped starter.

Each target after the suite is a separate configuration, not a fallback. --repeat 3 runs every case three times; --jobs 2 allows two agent trials at once. Each loop trial works its tasks in order. coop help eval run lists every option.

Understand failures before spending again

coop eval inspect reads the latest run; add a run ID to read an older one. It shows the trials that didn't pass, their recorded causes, and where to find saved diagnostics and kept workspaces.

  • failed: the independent verifier rejected the work.
  • error: running or grading couldn't produce a verdict. A provider's quota refusal is not a model-quality failure.
  • timed_out or pending: the trial ran out of time or didn't start. Grading is incomplete.

An incomplete comparison has no definitive winner. For sign-in or quota refusals, check coop credentials <agent>. For timeouts, check the case's suite.yaml budget as well as --timeout. A run without a final summary may be running or interrupted: you can inspect it, but you can't compare or resume it. Running again is a new paid run. Check the recorded provider output for private data before you share it.

Each trial gets a private workspace without the source's Git history. The hidden verifier is kept out of the model's mounts and runs afterwards in a separate container with no credentials or network. Your own MCP servers aren't exposed to trials. The agents' built-in web search and fetch are off, including for co:op's peers and delegates; terminal and file tools stay available. This is a control the trusted client applies, not a firewall that checks each request. Regular co:op runs are unchanged. Results describe this workload, not how providers compare in general; code size is a review signal, not a quality score.

Compare matching evidence

compare keeps the full requested denominator, including missing records. Duplicate records, or records outside the requested matrix, count as damaged evidence. Paired effects need two distinct runs with one configuration each, the same nonempty workload identity, case set and repetition count. Otherwise the results stay separate; co:op doesn't guess which configurations correspond.

A case's change needs every repeat graded; the aggregate change and its 95% bound need every requested pair graded. The bound measures repeat uncertainty on this fixed suite, assuming independent trials. It uses sqrt(log(40)/(cases*repeats)) around the pass-rate difference, clipped to the possible −100 to +100 percentage-point range. Repeats are not new independent tasks and don't establish performance on tasks the suite hasn't seen.

A decision campaign needs at least three repeats per case, plus a useful-effect threshold and a decision rule set in advance. Kept runs don't record that rule, so the report stays descriptive and inconclusive, with no definitive winner.

The loop

Give the agents a list of tasks and let them work through it on their own: through the night, through usage limits, without you at the wheel.

The problem it solves

Most real agent work isn't one big task but a queue of small, well-defined ones. Walking an agent through them by hand, one at a time, is the bottleneck. And one marathon session slowly degrades: the context fills with old work, the agent loses the plot, and quality slides. The loop avoids both.

Each task is a folder under .agent/tasks/, and the folder it sits in is its state. coop loop picks the next task and starts a fresh agent for it, so every task begins with a clean context. The agent does the work, runs your checks, commits the result and marks the task done. The loop keeps going until no task it can take is left, or until --max-tasks is reached. In a monorepo, list the members under subprojects: in a committed .agent/project.yaml, and one loop works every member's queue. Fill in each generated task.md before you start, so the agent knows what done means.

coop init                      # AGENTS.md, .agent/ and the hooks
coop tasks add "…"             # one folder per task
coop loop claude               # work the queue, then review it
coop loop claude --peer codex  # and let it ask a peer

It reviews its own work. When the queue is empty, a final review re-reads the tasks this run completed, checks that the Git history backs them up, and reopens anything that falls short. If it reopens work, the loop works the queue and reviews again, so done means checked, not just claimed. After three to five rounds, depending on how much the run did, a task that still falls short is blocked for your decision. Add your own checks under signoff.prompt in .agent/loop.yaml: a task that fails one (changelog updated, docs regenerated, no stray TODOs) is reopened.

It survives usage limits. Long runs hit subscription limits. Instead of failing, the loop reads the reset time from the agent's output and waits, or, if you've added another account, switches to it and keeps going. An overnight run rides through the limit instead of stopping.

It asks instead of guessing. For a call it shouldn't make alone, the agent blocks the task, which moves it to 50_blocked/, and writes a decision.md (the question, the options and its recommendation). The loop moves on to the other tasks. When nothing else can move, the loop stops and exits with status 3, so cron or CI can tell "waiting on a decision" from "done". coop tasks decisions -i walks you through each open decision, records your answer and unblocks the task; then run coop loop again, or start it with --preflight to unblock answered tasks first.

coop tasks watch shows the live board, including any running forks, while the loop works. For a status line in your shell prompt or tmux, coop prompt prints the repo's state on one line (task counts, and fork or loop activity); it only reads, so it's safe on every redraw.

Good fits

A backlog of small refactors. Moving one pattern across dozens of files. Working down a test-coverage or lint list. A Friday cleanup queue you'd never get to by hand. Anything that's many small, checkable steps.

The .agent/ folder

coop init creates a small folder, the same for every agent, that the agent reads on every start and after each compaction. The work queue (tasks/ and the backlog) is local working state that Git ignores; the knowledge and settings beside it are committed, so they travel with the project.

Path What it's for
tasks/ The work queue: a folder per task under 00_todo/, 10_in_progress/, 50_blocked/ and 99_done/. The folder a task sits in is its state; the numbers sort ls in order, and coop tasks shows the plain names. Local working state.
the backlog Work for later, as task folders in tasks/xx_backlog/ (coop backlog). Loops never pick it up; coop backlog promote <id> moves an item into 00_todo/ when it's ready.
kb/ The knowledge base: maps of each part of the code, and the traps and gotchas the code doesn't show. Agents keep it current as they work.
kb/rules/ Your taste, as rules: each correction becomes a "do X, not Y" card.
skills/ The workflow skills (spec, work, sweep, investigate, review-board, verify-api); each agent's own folder links to them.
presets/ Team recipes: a lead and its roles, like thinker, critic and fast. See Presets.
project.yaml Project settings: a monorepo's members, the dev server ports co:op publishes, the box's network setting, and the checks a fork must pass to merge.
loop.yaml The stages of coop loop (preflight, work, between, verify and signoff), and the models and prompts they use.

Parallel forks

One loop is one agent working one queue. Forks running in the background let several agents work the same queue at once, one task each.

Start one fork per agent, with --loop -d so it works the queue in the background. co:op hands each fork one task at a time from the shared .agent/tasks/ queue, so no two forks do the same work. coop tasks watch shows the tasks across every fork, coop fork ls each fork's state, and coop fork logs <name> -f its output.

coop fork api frontier --loop -d  # each fork takes the next task
coop fork web codex@work --loop -d
coop fork deps gemini --loop -d
coop tasks watch                  # tasks across every fork
coop fork merge --all             # merge all, checks first

Name a target (provider:model@account; give forks that run at once different accounts, so they don't share one limit) or a preset, whose lead ladder the fork's loop rotates through.

Why run parallel forks

Once writing code is cheap, reviewing it is the bottleneck. So run the writing in parallel and review in batches. Add agents until your review queue, not the agents, is what keeps you busy.

Editors

Prefer your editor to a terminal? co:op serves the sandboxed agent over ACP, so any editor that speaks the protocol can drive it. The agent runs in the box; its file and terminal requests to the editor follow the editor's own permissions.

ACP (the Agent Client Protocol) is an open standard any editor can adopt. coop acp [target|preset] speaks it over stdio, so you add co:op as a custom agent in an editor that supports ACP and steer it from there. Zed supports ACP today, and others are adding it. The setup is the same everywhere: one entry for each target or preset you use. In Zed's settings.json, for example:

{
  "agent_servers": {
    "coop": {
      "type": "custom",
      "command": "coop",
      // one target; pin it like "claude:opus/xhigh@work"
      "args": ["acp", "claude"]
    },
    "coop · second opinion": {
      "type": "custom",
      "command": "coop",
      // a named peer; the target pins the lead's model
      "args": ["acp", "claude:opus/xhigh", "--peer", "codex"]
    }
  }
}

Pin the model, reasoning effort and account in co:op's target inside args (provider[:model][/effort][@account]), not in the editor's own options. The toolbar menus start on that target, and you can still switch them. co:op always runs the agent without permission prompts, whatever the editor's permission setting.

co:op sits between the editor and the agent. A plain session's toolbar has Preset, Provider and Account menus; a session running a preset keeps the Preset menu. Switching accounts, or between models of one provider, keeps the conversation. Switching providers starts a new session and carries over the messages and a one-line note for each tool call, as closely as it can. The agent's own permission prompts are off; its file and terminal requests to the editor still follow the editor's permissions (see below). A usage limit is handled for you: co:op moves to your next signed-in account and sends your prompt again, or, if every account is at its limit, waits for the nearest reset. A box restart (coop build, coop update or running out of memory) replays the handshake, so your editor stays connected.

Over ACP, the agent can ask the editor to read or write files on your computer and run commands in its terminal. co:op passes those requests on, and the editor's permissions, not the box, limit them. For a boundary that is only the box, use a terminal or loop run. See the ACP security note.

Building a website? List the dev server's port under serve: in a committed .agent/project.yaml, and the thread shows the http://localhost:<port> address the box publishes it on. Bind the server to 0.0.0.0 inside the box.

Desktop apps don't always get your shell's PATH. If your editor can't find coop, use the full path from command -v coop as the command.

Toolchain and services

Real projects need a language toolchain and a database. Declare them once, instead of having the agent install them on every run.

If your repo pins versions in a .tool-versions file (asdf), coop init writes a .agent/Dockerfile that builds them into the box's image, so the agent never reinstalls them. coop init --stack asdf writes it even without the file.

Need Postgres or Redis alongside? They're opt-in (coop init asks, or pass --services postgres,redis), and they run in their own disposable containers that the box reaches by name:

coop up                    # start services, wait until healthy
coop claude                # reach them by their Compose names
coop down                  # stop services and keep their data
coop down --delete-volumes # delete their volumes, after asking

Agents can change data in any service they can reach, so use disposable development databases. Deleting service volumes asks you to confirm, and can't be undone.

When coop up finishes, it names the services Compose resolved, in Compose order. If Compose can't resolve them, co:op stops before starting anything and tells you what to fix.

coop update updates co:op itself, then rebuilds the box on fresh packages; coop update --box-only rebuilds just the box. coop build is the stable, pinned rebuild (coop build --egress filtered for a project with filtered networking). Each installs the agent versions your co:op release pins.

MCP and remote sessions

Share tool servers across agents, or connect a machine to a separate session controller.

Define MCP servers once, outside your repo. co:op makes them available to supported agents, within the network setting, and keeps eligible HTTP tokens outside the box. The MCP guide covers local commands, remote HTTP servers, tokens and network settings.

A remote worker connects out over TLS to a compatible controller, with coop sessions connect --controller <url> --token-file <path>. The controller supplies each job's repository, model targets, network access and limits; co:op fetches the code and runs the model. The worker keeps its private state and model credentials on its own machine, and needs Git, Git LFS and a supported container runtime. See the worker connector guide.

Configuration

Sensible defaults, and a few settings for when you need them.

Set these as environment variables or in ~/.config/coop/coop.conf; the last three work only as environment variables. The ones you're most likely to change:

Variable What it does
COOP_GATE Overrides the project's gate: checks on this computer, like make check.
COOP_EGRESS filtered lets the box reach only its AI provider and the destinations you approve; coop init sets it for the project. open, the built-in default, leaves the network open. none cuts the box off entirely: the agent can't reach its model, so use it to quarantine a box you suspect, then look inside.
COOP_RUNTIME Force docker or container instead of detecting one (detection prefers Docker).
COOP_MEMORY, COOP_CPUS Cap the box's memory and CPUs, like 4g and 2.
COOP_<AGENT>_MODEL An agent's default model everywhere it runs, like COOP_CLAUDE_MODEL=opus.
COOP_CAFFEINATE On by default: while a loop runs, macOS caffeinate keeps the machine from sleeping. Set 0 to turn it off.
COOP_HOMES On by default: each agent's home folder is mounted into the box. COOP_HOMES=0 keeps them out, so an agent can't read your agents' settings; presets and peers need them, so those runs stop with an error.
COOP_SPINNER On by default: the live spinners animate. Set 0 or false to freeze them, and the loop's fast redraws, while debugging or recording.
COOP_CONF Moves the coop.conf file co:op reads its COOP_* defaults from.
NO_COLOR Set to any value to turn off color everywhere (no-color.org).

On Docker, the box also runs with every Linux capability dropped, no-new-privileges and a process limit. The README reference lists every variable.

Troubleshooting

What trips people up, and the quickest fix for each.

Symptom Fix
"no container runtime found" Install Docker or Apple container, then run coop build --egress open && coop doctor.
"image … not built" Run the coop build command the message names: --egress open, or --egress filtered for a project with filtered networking.
Sign-in hangs, or "usage limit reached" Run coop login <agent> again. A subscription limit resets on a schedule, and a loop waits for it on its own.
A background loop won't stop Watch it with coop fork logs <name> -f, and stop it with coop fork stop <name>.
A secret is still visible Add its path to .coopignore. coop check-secrets finds secrets hiding inside files.

The README has the full troubleshooting guide and every command's flags, and coop help (or coop <command> --help) is the live reference.
